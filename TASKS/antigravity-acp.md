# Spike: Antigravity CLI (`agy`) through ACP

**Priority:** P2
**Status:** Phase 1 implemented (2026-11-17): `src/core/acp-session.ts`,
`src/core/acp-transcript.ts`, the `agy` harness wiring, and tests against a
fake ACP agent. It was verified end to end against real `agy` 1.5.10 on
`framework`. Phase 2 (importing TUI conversations, staleness, recovery) and
phase 3 (detached relay) remain. The owner has accepted the terms risk of
programmatic prompts (see Owner decision).

## Goal

Use an Antigravity subscription from pi-dish without the pattern Google bans:
a third-party harness reusing Antigravity OAuth tokens. The candidate is to
drive Google's own, unmodified `agy acp` binary as an
[Agent Client Protocol](https://agentclientprotocol.com) server, with pi-dish
acting as an ACP client the same way Zed or JetBrains do. `agy` keeps its own
sign-in, tools, settings and transcript store.

## Verdict

ACP is the correct mechanism, and Google has approved it for consumer sign-in
(`oauth-personal`, the Pro/Ultra subscription). Google staff approved T3
Code's ACP integration on architectural grounds: an ACP client that launches
the official, unmodified binary with its native sign-in. The approval is not
specific to T3 Code; a Google maintainer extends it to any interactive ACP UI,
which pi-dish's design matches. Every statement scopes it to "single-user
interactive development", with Gemini models only. Prompts generated by
agents or schedules fall outside that scope.

### Owner decision (2026-11-17)

`agy` sessions get the same prompt sources as every other harness: browser
prompts, peer-agent messages and holds, `pi-dish-sessions` spawns,
`#ref` delegation, routines and recovery auto-continue. pi-dish does not gate
on prompt origin. The owner accepts that, per the maintainer answer below,
agent-generated prompts on `oauth-personal` are a §6 breach subject to
automated enforcement and possible suspension. Switching `agy` to
`gemini-api-key` or `agent-platform` removes that exposure without code
changes.

### Terms boundary (primary sources)

- [Additional Terms §6](https://antigravity.google/terms): "Using third party
  software, tools, or services to access the Service (e.g. using OpenClaw
  with Antigravity OAuth) is a breach of this Agreement."
- [FAQ](https://antigravity.google/docs/faq): "Wrapping `agy` inside
  third-party coding agents or applications … is not supported under consumer
  plans"; violations "can result in suspension or termination".
- A Google maintainer clarified the line in
  [antigravity-cli#1493](https://github.com/google-antigravity/antigravity-cli/issues/1493)
  (2026-11-12):
  - Permitted: "Any interactive ACP v1 client, including … custom or
    non-editor interactive ACP UIs, may launch the unmodified `agy acp`
    binary when a human user is directly driving the session." The
    accept-edits and auto modes are fine "within a session you initiate and
    supervise yourself".
  - Not permitted on `oauth-personal`: "using `agy acp` as a backend worker
    inside a third-party coding agent, autonomous agent harness, or background
    orchestrator"; "another agent, autonomous loop, or background task queue
    generat[ing] prompts"; "overriding Antigravity's system identity
    instructions"; and "automating account rotation". There is "no carve-out
    for single-account or personal use", and such traffic "is subject to
    automated abuse enforcement".
  - Unrestricted alternatives: `gemini-api-key` (`GEMINI_API_KEY`) and
    `agent-platform` (GCP ADC), which fall under the API and Cloud terms.
- Google staff on the Gemini forum, about T3 Code specifically:
  - [192027](https://discuss.ai.google.dev/t/tos-clarification-is-t3-code-official-antigravity-acp-agent-permitted-under-the-antigravity-terms-of-service/192027)
    (2026-10-26): "using T3 Code with your personal Antigravity subscription
    is permitted for your own single-user, interactive development, as long
    as it runs the official `antigravity-acp` binary … and signs in through
    its native OAuth flow". The reason given is "architectural": the client
    "communicates over standard JSON-RPC with our unmodified `antigravity-acp`
    agent binary".
  - [189889](https://discuss.ai.google.dev/t/supported-gemini-subscription-access-for-a-third-party-vs-code-extension/189889)
    contradicts itself. Google's 2026-10-29 reply, edited on 10-30, says using
    T3 Code with an Antigravity login violates the terms. The same staff
    member then clarified on 11-02 that T3 Code "is permitted specifically
    when it acts as an ACP client launching Google's official, unmodified …
    binary … for single-user interactive development", with "model selection
    scoped to the Gemini models included in your plan". Claude models remain
    restricted to first-party surfaces.
  - A follow-up in 192027 asking whether any client built the same way is
    covered is unanswered there. The #1493 answer above covers it: "custom or
    non-editor interactive ACP UIs".
- The #1493 reporter's follow-up asked whether a framework injecting a system
  prompt and history counts as a harness. **That question is unanswered.**
  pi-dish should not inject any prompt text into `agy` sessions.

Automated enforcement can only classify traffic it sees. This spike cannot
verify how Google detects it. `agy` sends ACP `clientInfo` upstream in its own
client metadata **[INFERENCE: from `ClientInfo` protobuf symbols in the binary,
not observed on the wire]**, so pi-dish must identify itself honestly.

### Hard rules for any implementation

1. Launch the unmodified `agy acp`. Never use `--override_user_agent_name`
   (present in `agy acp --help`). Never send a `clientInfo` that impersonates
   another client. t3code sent `{name:"zed"}` to `agy` below 1.5.1 to unlock
   non-Gemini models; do not copy this.
2. Never read, copy or refresh `agy`'s token files (`acp_token.json`, keyring
   entries). t3code's usage-limit probe does this; do not copy it.
3. Do not use `_meta.antigravity.systemPrompt.append`, even though `initialize`
   advertises it. Do not inject preambles, skills text or history into prompts.
4. One account per pi-dish host. Never rotate accounts.

## Executable spike results (2026-11-17)

Environment: `agy` 1.5.10 installed with the official `install.sh --dir` into
`/tmp/agy-spike/bin` with `HOME=/tmp/agy-spike/home`. No sign-in. No model
request was sent. A Node probe sent `initialize`, then `session/new`, then
`session/list` over stdio.

`initialize` with `clientInfo {name:"pi-dish"}` and no `fs`/`terminal` client
capabilities returned:

```json
{
  "protocolVersion": 1,
  "agentInfo": { "name": "Antigravity ACP Server", "version": "1.5.10" },
  "agentCapabilities": {
    "loadSession": true,
    "promptCapabilities": { "image": true, "audio": false, "embeddedContext": true },
    "sessionCapabilities": { "resume": {}, "close": {}, "load": {}, "list": {}, "additionalDirectories": {} },
    "auth": { "logout": {} },
    "_meta": { "antigravity": { "tier": true, "systemPrompt": { "append": true } } }
  },
  "authMethods": ["oauth-personal", "oauth-business", "gemini-api-key", "agent-platform"]
}
```

(`authMethods` is abbreviated to ids. The binary also sends snake_case
duplicates of the capability keys.)

- Without credentials, `session/new` and `session/list` both fail with
  `{"code":-32000,"message":"Authentication required"}`. The log records
  "Silent sign-in failed; session requests fail with auth_required until the
  client signs in." `terminal-login` is not offered when the client does not
  advertise terminal auth.
- Startup takes about 90 ms (`initialized server successfully in 88ms`). One
  idle, unauthenticated `agy acp` process has about 170 MB RSS. Memory with an
  authenticated session is unmeasured.
- On first run `agy` creates `~/.gemini/config/` and
  `~/.gemini/antigravity-cli/{conversations/,brain/,implicit/*.pb,conversation_summaries.db,builtin/,installation_id}`.
  Conversations are protobuf/SQLite, not JSONL. The ACP backend also tries to
  read `~/.gemini/antigravity/conversations`.
- In this SSH session `agy` chose file-based token storage ("Using file-based
  token storage because SSH session detected").
- The default CCPA endpoint in `--help` is `daily-cloudcode-pa.googleapis.com`.

### Signed-in capture (2026-11-17, `framework`, Google AI Ultra)

The owner signed in with `oauth-personal`, ran `agy` 1.5.10 on `framework`,
and had the spike drive throwaway recorders. Both runs sent
`clientInfo {name:"pi-dish"}` and no `fs`/`terminal` capabilities, and
worked in scratch git repos. The raw frames are in
[`docs/agy-acp-capture/`](../docs/agy-acp-capture/):
- `live-turns.jsonl`: both directions; default permissions, elicitation not
  advertised.
- `load.jsonl` and `resume.jsonl`: replays of that session.
- `yolo-elicit.jsonl`: both directions; `--dangerously-skip-permissions`
  with `elicitation.form` advertised.

The frames contain no tokens or email addresses; the only account data is
the tier name.

- **`session/new`** returns `modes` (`default`, `accept-edits`, `auto`,
  `plan`; current `default`), `models.currentModelId`
  (`gemini-4-carbon-medium`) and three `configOptions`:
  - `model`: `gemini-4-carbon`, `gemini-4-argon`, `gemini-4-hydrogen`,
    `gemini-pro-orchestrator`, `gemini-pro-orchestrator-argon`,
    `gemini-3.8-flash`, `claude-sonnet-4-6`, `claude-opus-4-6-thinking`,
    `gpt-oss-120b-medium`
  - `thought_level`: `low`, `medium`, `high`
  - `mode`

  **Claude and GPT models were offered to pi-dish**, despite the docs and the
  11-02 forum reply saying non-Gemini models are limited to first-party
  surfaces. **Owner decision (2026-11-17):** pi-dish offers only the `gemini-*`
  values of the `model` option and hides the Claude and GPT entries.
- **`session/list`** with cwd `/tmp/agy-capture` returned the owner's TUI
  conversation from cwd `/home/jyarwood` (id, cwd, title, `updatedAt`). TUI
  conversations are therefore listed across workspaces. The store is
  `conversations/<uuid>.db`, SQLite with protobuf blobs in `steps`; pi-dish
  must not parse it.
- **`available_commands_update`** lists `goal`, `compact`, `schedule`,
  `browser`, `plan`, `grill-me`, `teamwork`, `learn`, `boost`,
  `agy-customizations`, `antigravity-guide`, `run-workflow` and `swarm`.
  `compact` is present, unlike t3code's docs.
- **Tool calls** carry non-ACP `name` and `args` fields with `agy`'s native
  tool names (`read_file`, `edit_file`, `write_file`, `run_command`,
  `ask_question`) and argument keys (`Path`, `Target`/`Replacement`,
  `Content`, `CommandLine`), alongside ACP's `kind`, `title`, `locations` and
  `rawInput`. pi-dish's renderers (`src/browser/tool-format.ts`) only
  special-case `bash`, `eval` and `wait` and read `args.command`, so these
  need normalising (see Event mapping). Status moves
  `in_progress → pending` (waiting for permission)
  `→ in_progress → completed | failed`.
  - Edit completions carry `content:[{type:"diff",path,oldText,newText}]`
    (whole file).
  - `run_command` completions carry text content plus
    `rawOutput {output, exit_code}`.
  - Reads finish with no content.
- **Permissions:** in `default` mode, `run_command` produced
  `session/request_permission` with options `allow`/`allow_once` and
  `deny`/`reject_once`, and `toolCall` set to the pending tool call. Edits in
  the workspace were not prompted. Deny made the tool `failed` with empty
  output, and the turn ended `end_turn`.
- **Questions:** without client elicitation support, `ask_question` (args
  `questions[{question, options[], is_multi_select}]`) parks in `pending`.
  The question is streamed as assistant text and the turn ends `end_turn`.
  The next user prompt is consumed as the answer, and the tool then
  completes. pi-dish can render the pending `ask_question` as an `ask`
  dialog whose answer is sent as the next prompt.
- **Steer:** a `session/prompt` sent during a running turn takes the turn
  over. In `live-turns.jsonl`, prompt id 9 was running. Steer id 10 was sent
  at …348312, and **id 9** returned `{stopReason:"end_turn"}` with no usage
  2 ms later. Id 10 carried the rest of the turn and returned `cancelled`
  with usage at …381910. The turn therefore ends with the response to the
  newest outstanding prompt. An earlier prompt's no-usage `end_turn` is a
  handover, not the end of the turn.
- **Cancel:** `session/cancel` (…381907) made the newest prompt return
  `stopReason:"cancelled"` with usage 3 ms later.
- **Usage:** `PromptResponse.usage` gives `inputTokens`, `outputTokens`,
  `cachedReadTokens`, `cachedWriteTokens`, `thoughtTokens` and
  `totalTokens`. `usage_update` gives `{used, size}` context (`size`
  1048576).
- **`session_info_update`** sets the title after the first prompt.
- **`session/load`** (707 ms, fresh process) replays history as
  `user_message_chunk` per user prompt, `agent_message_chunk` and thought
  chunks, and `tool_call` frames already in their final `completed`/`failed`
  state, including diff and command content. It sends no
  `tool_call_update`s and no prompt results. All 8 tool calls replayed,
  including `ask_question`. The replay is still lossy: the user's
  "1. Also add…" prompt (consumed as the question answer) and the question's
  streamed assistant text are missing. Write the mirror from the live stream,
  and use `load` only to import sessions started elsewhere.
- **`session/resume`** (567 ms) replays nothing (only commands and title),
  as documented.
- Turns were slow: 20–60 s each, even for a one-line read.

## Documented `agy acp` behavior

From the [ACP guide](https://antigravity.google/docs/ide/extensions/acp):

- It uses ACP v1 over stdio, with the project directory as cwd.
- Session options are **Model** and **Thinking level**. The docs list
  `Low`/`Medium`/`High`/`Extra`/`Max`, but 1.5.10's `thought_level` option
  offered only `low`/`medium`/`high`, and model ids such as
  `gemini-4-hydrogen-xhigh` carry their own effort. The picker must take its
  levels from `configOptions`, not from these docs. "Gemini models are
  available in every client. Third-party models are only offered to
  JetBrains IDEs …, Android Studio, …, Zed, and Xcode."
- "Sending a prompt while a turn runs steers that turn." This maps directly to
  pi-dish steer. ACP has no follow-up queue.
- Cancel ends open tool calls and abandons pending permission requests.
- Permission requests offer Allow and Deny. Rules in `agy`'s own settings still
  apply. `--dangerously-skip-permissions` exists.
- `agy` supports load, resume (no history replay), list and close for
  sessions.
- Agent questions use ACP elicitation forms when the client supports them,
  otherwise they appear as chat text.
- Useful flags: `--add-dir`, `--agent`, `--sandbox`, `--process-per-session`,
  `--log-file`, `--disable-telemetry`. Logs go to
  `~/.gemini/antigravity-cli/log/acp-*.log`.
- Over SSH, sign in once with `agy acp --login` (paste-a-code flow).

## Reference implementation: t3code

[pingdotgg/t3code](https://github.com/pingdotgg/t3code) (PR
[#9348](https://github.com/pingdotgg/t3code/pull/9348), docs
[providers-antigravity](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-antigravity.md),
[providers-acp](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-acp.md))
is a real ACP client. Worth copying:

- One `agy acp` child per thread, with cwd set to the project. Generic client:
  `packages/provider-acp/src/server/AcpSessionRuntime.ts`; agy layer:
  `apps/server/src/provider/acp/AntigravityAcpSupport.ts`.
- Client capabilities: `fs.readTextFile` limited to cwd and attachments,
  `fs.writeTextFile:false`, `terminal:false`. Edits arrive as tool-call diffs.
- Prefers `session/resume` over `session/load` because load replays tool calls.
- Model and thinking are set with `session/set_config_option`; the lists come
  from `session/new` `configOptions` (fallback `models`).
- Modes in 1.5.4+: `default`, `accept-edits`, `auto`, `plan`.
- Cancel waits for the in-flight `session/prompt` to settle before the next
  prompt is sent. If cancel times out, the process is retired.
- Requests with `interaction_*` tool-call ids are questions, not permissions.
  "Allow always" wording comes from `_meta["agy.security.warning"]`.
- `agy` cannot rewind, so t3code's "edit from here" starts a new session and
  resends the kept turns. pi-dish must not copy this, because it injects
  history (rule 3).
- Sign-in: the stdout line `Open the following link to authenticate the ACP
  server: <url>`, then the remote `127.0.0.1` callback paste.

Avoid copying the version-gated `clientInfo:"zed"` spoof, the
`acp_token.json` usage probe, and the default of `oauth-personal` with no
terms warning. t3code's docs never mention §6.

## Proposed pi-dish design (option C)

pi-dish already supports three transports behind one structural `LiveSession`
union (`src/core/session-ownership.ts`): Pi bridge, Pi RPC child
(`rpc-session.ts`) and the Prime daemon (`prime-daemon.ts`). The RPC and Prime
transports extend `TransportSession` (`src/core/transport-session.ts`), which
already owns `turnInProgress`, `runningToolCalls`, `extUIState`, and the
delta-to-full-message `assistantFrame()`. An ACP transport is a fourth sibling
of the same kind and needs no new abstraction.

### Descriptor and process model

- Add `HarnessId` `agy` with `liveTransport:'acp'`, `command:'agy'`
  (overridable with `PI_DISH_AGY_COMMAND`) and `closeMode:'owned-agent'`.
  `HarnessDescriptor.argv.new/resume/models` is required
  (`contracts.ts:177-180`). Either make it optional for transports that
  never launch through tmux, or supply the `agy acp` argv there (Prime still
  fills it).
- Run one `agy acp --dangerously-skip-permissions --disable-telemetry
  --log-file <dish log dir>/agy-<session>.log` child per live session (the
  flag takes a file), with cwd set to the session cwd. This matches RPC
  ownership: close means `session/close` then SIGTERM, and a hung turn
  affects only its own process. Memory is the cost (≥170 MB each). Revisit
  `--process-per-session` with one shared front if that becomes a problem.
- Record `agentInfo.version` from every spawn in the mirror header and the
  sidecar. Warn in the session (status line) when it differs from the
  versions the fixture was captured on. `agy` updates itself, and the
  `name`/`args` fields and the `q1`/`q1_other` schema are not part of ACP.
- **Permissions (owner decision, 2026-11-17):** always skip them, matching
  how pi-dish runs Pi and OMP. Verified on `framework` (`yolo-elicit.jsonl`):
  with the flag, `run_command` and `write_file` ran with no
  `session/request_permission`, while the advertised mode stays `default`.
  pi-dish still answers an unexpected permission request by showing it as a
  `select` dialog rather than hanging the turn.
- Do not set `GEMINI_HOME`/`--gemini-dir`. pi-dish uses the user's normal
  `agy` profile, so the TUI and pi-dish share one sign-in and one account.
  Strip ambient `GEMINI_API_KEY`/`GOOGLE_*` unless the configured auth method
  needs them, so the auth method is never chosen by accident.

### Handshake

`initialize` sends `{protocolVersion:1, clientInfo:{name:"pi-dish",
title:"pi-dish", version}, clientCapabilities:{fs:{readTextFile:false,
writeTextFile:false}, terminal:false, elicitation:{form:{}}}}`. Fail closed
unless `agentInfo.name === "Antigravity ACP Server"`, `loadSession` is true
and `sessionCapabilities.resume` is present.

If a request fails with `-32000` and the message "Authentication required"
(`-32000` alone is generic), report "agy is not signed in; run `agy` or
`agy acp --login` on <host>". pi-dish does not run OAuth itself in phase 1.

### Event mapping

| ACP | pi-dish |
|---|---|
| `session/prompt` sent while idle | `agent_start` + `turn_start` + user `message_end`; record it as the turn's newest prompt id |
| `session/prompt` sent during a turn | steer: user `message_end`, and it becomes the newest prompt id. agy then answers the previous prompt with a no-usage `end_turn`, which is ignored. |
| `agent_message_chunk` / `agent_thought_chunk` | Open an assistant segment if none is open (`message_start`), then `assistantFrame()` → coalesced `message_update` (text / thinking blocks) |
| `tool_call` | If an assistant segment is open, append the `toolCall` block and close it (`message_end`), since ACP interleaves text and tools and Pi needs the assistant message before its tool results. Then `tool_execution_start` with the normalised name and args (below). The next chunk opens a new segment. |
| `tool_call_update` (`in_progress`, content/diff) | `tool_execution_update` (latest-wins, existing 50 ms lane) |
| `tool_call_update` `completed`/`failed` | `tool_execution_end` (`isError` on failed) |
| `plan` | `extension_ui_request` `setWidget` (read-only plan list) |
| `available_commands_update` | `getCommands()` cache for the slash picker |
| `current_mode_update`, `config_option_update` | state for model/thinking/mode pickers |
| `usage_update` `{used,size}` | context meter (`lastStats`) |
| `session_info_update` (title) | session name |
| Result of the **newest** prompt | Close the open segment (`message_end`, with the prompt's usage on the last assistant message), then `turn_end` + `agent_end`. `cancelled` = aborted; `refusal` is shown like an OMP classifier refusal. |
| inbound `session/request_permission` (not expected with the flag) | `extension_ui_request` `select` over ACP `options[]`; `respondExtensionUI` → `{outcome:{outcome:"selected", optionId}}`; dismissed → `cancelled` |
| inbound `elicitation/create` (`mode:"form"`) | `extension_ui_request` `ask`, built from `requestedSchema`. Each non-`_other` property is a question: its `title`, plus option labels from its `oneOf[].title`. The schema doesn't mark a recommended option, so that comes from the pending `ask_question` call (matched by `toolCallId`): an option with a `(Recommended)` prefix gets that prefix stripped and its index set as `recommended`. Answer mapping: browser `selectedOptions` labels → their `oneOf` `const`, and `customInput` → `<key>_other`, sent as `{action:"accept", content}`. The browser's `{kind:'chat'}` maps to `decline`, and a dismissal to `cancel`. The turn continues in place. The multi-select schema shape has not been observed. |
| child exit | `session_ended` |

**Tool normalisation.** The pi-dish `toolCall`, `tool_execution_*` and
`toolResult` records use pi-dish's existing tool vocabulary so the current
cards render. `agy`'s native call is kept in the sidecar.

| agy `name` | pi-dish `toolName` |
|---|---|
| `run_command` | `bash` with `{command: CommandLine}`; `exit_code` → bash details |
| `read_file` | `read` with `{path: Path}` |
| `edit_file` | `edit` with `{path, oldText: Target, newText: Replacement}` |
| `write_file` | `write` with `{path, content: Content}` |
| other names | passed through; `title` is the display label |

**`prompt()` contract.** `AcpSession.prompt()` resolves once the request is
written, not when ACP answers. That answer comes at turn end, which in the
capture took 20–60 s or more, and steer can hand the turn to a later
prompt. Turn completion is tracked through events. There is no 120 s RPC
timeout (`rpc-session.ts:188`). `message-hold.ts:109` and
`routine-runner.ts:309-311` await `prompt()` and then behave as they do for
the other transports.

Commands: `abort` → `session/cancel` (notification) followed by awaiting the
newest prompt's response. `setModel`/`setThinkingLevel` →
`session/set_config_option`. Mode → `session/set_mode`. `setName`, compact,
tree, queue cancel and follow-up queueing are unsupported (capability false).
Slash commands are sent as prompt text, as Zed does.

### History

ACP exposes no transcript file. Every pi-dish history surface (messages,
search, usage, comments, export, shares) reads Pi-format JSONL through
`session-files`/`session-index`.

- **Recommended: translate at write time.** pi-dish writes a Pi-format JSONL
  mirror (`~/.pi/dish/agy/sessions/<agySessionId>.jsonl`) and points the
  descriptor's `rootPath` at it, so discovery and every reader work unchanged.
  It is small because the transport already builds Pi-shaped messages for SSE:
  the assistant segments (see Event mapping) close at each tool call and at
  turn end, and tool completion carries the result. The writer appends what is
  already emitted, in emission order, so an assistant message is always
  written before the `toolResult`s for its `toolCall`s:
  - a `{"type":"session","version":3,id,cwd,timestamp}` header, plus the
    `agy` version;
  - user `message_end` → `{type:"message", message:{role:"user", content}}`;
  - assistant `message_end` → `role:"assistant"` with text, thinking and
    `toolCall` blocks (normalised `name`/`arguments`), `model` from the
    `model` config option, `provider:"google-antigravity"`, and `stopReason`
    and `usage` on the turn's last segment. `PromptResponse.usage` maps to
    `input`, `output`, `cacheRead`, `cacheWrite` and `reasoning`. Add
    `agy: {'google-antigravity': true}` to `PLAN_PROVIDERS`
    (`harness-pricing.ts:51`, where OMP already lists `google-antigravity`) so
    zero rates read as "plan" rather than `costUnavailable`;
  - `tool_execution_end` → `role:"toolResult"`, `toolCallId`, `toolName`,
    `content` (text, command output, or the edit diff rendered as text),
    `isError` for `failed`;
  - `model_change`, `thinking_level_change` and `session_info` entries when
    the config options or title change.

  Entries chain `id`/`parentId` linearly (no tree). The estimate is about
  150–250 lines plus tests. This is the first pi-dish-owned transcript
  writer, and it writes only under its own root. `agy`'s store stays
  authoritative.
- **Raw sidecar:** append every ACP frame **in both directions** as
  `{t,dir,msg}` to `<id>.acp.jsonl` beside the mirror, as the capture does.
  User prompts and elicitation answers exist only in outbound frames (live
  sessions emit no `user_message_chunk`). No reader touches it. It allows
  the mirror to be rebuilt if the translation is wrong or improves, since
  `session/load` replay is lossy.
- **Rejected: ACP as an alternative read format.** ACP is a stream of chunks,
  not messages: one assistant message spans many frames, and steer and
  question answers interleave. Reading it would mean reassembling it in
  `parseSessionEntries` and keeping that correct through the incremental
  readers (`extendSearchIndexFromEntries`, `extendIndexedUsageFromEntries`,
  `readSessionTailEntry`, tree/leaf reads) and the modules that parse
  transcript lines themselves (`session-discovery`, `session-index`,
  `session-hibernation`, `recovery-runner`, `omp-export`). The existing
  `SessionFileProfile` mechanism (`omp-v1`) covers small differences in entry
  shape, not a different record model.
- Sessions started outside pi-dish come from `session/list`. They are
  imported into the mirror on first open with `session/load`. Replay needs
  its own rules in the same writer:
  - `user_message_chunk` starts a user message and closes the previous
    message;
  - a `tool_call` already `completed`/`failed` counts as start plus end;
  - the `session/load` response flushes the open message.

  Later live use goes through `session/resume`.
- **Staleness:** `session/resume` replays nothing, so turns taken in the
  `agy` TUI never reach the mirror on their own. On open, compare
  `session/list` `updatedAt` with the mirror's last entry. If it is newer,
  re-import through `session/load` into a fresh mirror (the old one and its
  sidecar are kept), and mark the transcript "imported, lossy".
- Rejected: replaying history through `session/load` on every view. That
  spawns an authenticated process per read, breaks search and usage, and adds
  backend traffic that is not driven by a human.

### Restart behavior

Owned children die when pi-dish restarts, as RPC sessions do today (no spawn
record; `closeResources` does not adopt them). Phase 1 accepts this. After a
restart a session shows as inactive, and the next human prompt respawns
`agy acp` and runs `session/resume`. A turn running during a pi-dish update is
lost. A later phase can add a small detached relay that owns `agy`'s stdio
behind a Unix socket (the bridge-socket pattern) so turns survive updates.
Hibernation must skip `agy` sessions mid-turn.

### Prompt sources

No origin gate. Every existing route (`session-command-handlers.ts`,
`routine-runner.ts:309-311`, `message-hold.ts:109`, `POST /api/sessions/new`)
treats `agy` like any harness, subject only to the transport's capability
table and the `prompt()` contract above.

Recovery does not work yet: `recovery-runner.ts:240` and `:341` hard-code
`['pi','omp']`, so `agy` currently gets "no verified recovery prompt path"
or a 409. Add `agy` there and give it a resume path: respawn, then
`session/resume`, then prompt, since owned children do not survive a
restart.

### Size and containment

The comparable precedent is Prime's daemon transport (`72bdd54`). It changed
18 `src/core` files (+1604/−320, with `prime-daemon.ts` at 634 lines) plus
fixtures and tests. ACP is about the same size: it has no tmux adoption or
roster ownership, but it adds the mirror writer, assistant segmentation, tool
normalisation and the question mapping.
`TransportSession` (`18db751`) already gives RPC and Prime a shared base, and
`AcpSession` extends it unchanged.

The change is additive for the Pi lineage:

- **Unchanged:** the bridge extensions, `rpc-session.ts`,
  `prime-daemon.ts`, `session-files`/`session-index` parsers, SSE coalescing
  and the browser renderers. The mirror emits existing Pi entry shapes, so no
  parser learns an ACP shape.
- **Shared files that gain an `agy`/`acp` branch:** the dispatch points that
  already branch for Prime or by harness (`session-ownership.ts`,
  `session-launch.ts`, `session-operations.ts`, `session-catalog-runtime.ts`,
  `session-stream-handler.ts`, `live-sessions.ts`, `session-capabilities.ts`,
  `session-hibernation.ts`, `session-source.ts:129`, `session-read-handlers`,
  `session-mutation-handlers`, `session-slash-handlers`,
  `session-tree-handlers`, `model-feature-handlers`, `helper-models`,
  `publication-handlers`), plus the harness lists in `recovery-runner.ts`
  and `harness-pricing.ts`. This is the regression surface, and `npm test`
  plus `npm run test:lineage` cover it.
- **Closed unions:** `HarnessId` and `liveTransport` in `contracts.ts`. The
  compiler catches exhaustive switches and `Record<HarnessId, …>` maps. The
  `if` chains on `liveTransport === 'prime-daemon'` need a manual review.

A fourth transport is where a small transport registry would replace the
repeated `instanceof`/`liveTransport` chains. That is a separate refactor
stage, not part of this change.
